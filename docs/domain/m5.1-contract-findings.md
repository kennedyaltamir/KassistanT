# M5.1 Contract Findings

## CONTRACT-001 — DomainOutbox

**Classification:** Contract / Documentation inconsistency.

**Predominant contract:** The consolidated architecture repeatedly defines `InboundInbox`, `DomainOutbox`, `JobQueue`, `EventBus`, and `AuditLog` as distinct boundaries. `DomainOutbox` is also described as the persistence boundary for external effects created by domain transactions.

**Conflicting text:** Section 24 of the v1.0.1 baseline states that the MVP does not use `DomainOutbox/Event Sourcing`, which conflicts with the repeated architectural definition of `DomainOutbox` elsewhere in the same baseline.

**Impact:** The M5.1 persistence foundation may establish generic migration/transaction primitives, but the exact domain behavior and schema of `DomainOutbox` must not be finalized from the conflicting text alone.

**Decision for M5.1:** Do not implement DomainOutbox domain behavior in this increment.

---

## CONTRACT-002 — `order.status_changed`

**Classification:** Contract / Documentation inconsistency.

**Predominant contract:** `order.status_changed` appears in the canonical event catalogue and in the consolidated domain event contracts already materialized in `packages/contracts/src/events.ts`.

**Conflicting text:** Section 74 of the v1.0.1 baseline states `Não existe order.status_changed`, while the same section and other sections refer to `order.status_changed` again.

**Impact:** The M5.1 persistence foundation must not finalize Order Engine event persistence semantics from the conflicting sentence.

**Decision for M5.1:** Preserve the existing event contract and defer Order Engine event finalization until the documentation inconsistency is resolved through the project governance process.

---

## Scope

These findings do **not** alter the approved architecture. They record inconsistencies already present in the approved baseline so implementation can continue without silently redefining the contract.
